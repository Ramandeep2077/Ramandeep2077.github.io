Multi-Stage Security Regression Tracker

A cloud-native platform on AWS that catches the “we fixed it in staging, but it’s back in prod” class of bug by diffing static and dynamic security scans across environments.

The problem

Applications move through environments: dev, then staging, then production. A security fix made in one environment doesn’t always reach the next. A bad merge, a config rollback, or a rushed hotfix can quietly undo it, and a vulnerability that was already fixed reappears in production.

These security regressions are dangerous because they’re silent. Existing scanners look at one codebase or one deployment at a time, so none of them notices that a fix was lost between environments.

The solution

The platform scans all three environments through two lenses, stores every finding in one table, and diffs adjacent environments for each tool:

  • SAST (static): reads source code for vulnerable patterns such as hardcoded secrets.
  • Pentest (dynamic): probes the running app over HTTP for weaknesses such as missing security headers or rate limiting.

Key idea: any finding present in a later environment but absent in the earlier one is a regression. HIGH-severity regressions email the team automatically.

Everything is Infrastructure as Code in Terraform (three stacks: SAST, pentest, integration) with one-command build and teardown, monitored through CloudWatch Logs and Container Insights.

My part: the SAST pipeline

I built the static-analysis side as a serverless pipeline: source code is posted to API Gateway, a Lambda function scans it for vulnerable patterns, and the findings are written to the shared DynamoDB table under <env>#SAST. Because static scanning is fast and stateless, Lambda fits it well: it scales automatically and costs nothing when idle. Amritasingh built the pentest pipeline on Fargate, and the shared table schema is what joined our two pipelines into one platform.

Key design decisions

  • Match compute to the workload. Static scans are quick and stateless, so they run on Lambda. Dynamic scans are container-based, network-heavy and longer-running, so they run on Fargate, avoiding Lambda’s 15-minute limit.
  • One shared data contract. A parameterized scanType sort key lets SAST and pentest results live in one table and be compared directly.
  • Environments through configuration. SAST scans three source versions, and the pentest runs one Docker image toggled by environment variables (SECURE_HEADERS, RATE_LIMIT).
  • No public exposure. The vulnerable target and the scanner run in the same Fargate task and talk over localhost, with no load balancer.
  • Near-zero idle cost. Lambda, DynamoDB, API Gateway and SNS are serverless, and Fargate tasks run only on demand.

Security improved sharply from dev to staging, but production brought two issues back:

  • Hardcoded secret (SAST, HIGH): fixed in staging, back in prod. This triggered the SNS email alert automatically.
  • Security headers (pentest, MEDIUM): passing in staging, failing in prod.

The integrated services were Lambda, ECS/Fargate, ECR, DynamoDB, API Gateway, SNS, CloudWatch, IAM and VPC.

What I learned

  • localhost inside a container is the container itself, not the host; containers in the same task share it.
  • When to choose Lambda versus Fargate, and how Infrastructure as Code makes a multi-component system repeatable and cheap to run.

What I’d improve next

  • Least-privilege IAM roles per component, instead of the broad lab role
  • Retries and dead-letter handling (Step Functions or SQS) for failed scans
  • A normalized findings schema shared by both tools
  • A dashboard UI and automatic triggering through an EventBridge schedule or a GitHub webhook
